# REVIEW.md

## Defects Found in the Starter Code

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes()` | The calculation depends on the timestamp's timezone and does not normalize instants to whole seconds as required by the contract. | Submit epoch-millisecond timestamps with fractional seconds or timestamps near an IST date boundary and compare the expected late minutes and attendance date. | Normalize incoming timestamps to whole seconds and use IST consistently for attendance calculations. |
| 2 | `compute_work_hours()` | Python's built-in `round()` uses ties-to-even rounding, which does not implement the required half-up rounding rule. | Test a duration whose work hours fall exactly on a rounding tie, such as a value ending in the relevant half-cent increment. | Calculate work hours using the contract's half-up rounding rule. |
| 3 | `compute_overtime()` | The shift-end calculation assumes the shift ends on the same calendar date. It does not correctly handle overnight shifts. | Create an employee whose shift ends after midnight and punch out after that shift end. | Build the shift-end instant using the employee's shift and attendance date, advancing the end date when the shift crosses midnight. |
| 4 | `create_employee()` | Checking for an existing employee before inserting is not atomic. Concurrent requests with the same `emp_code` can both pass the check. | Send two concurrent requests with the same `emp_code`; both may pass the initial lookup without a database uniqueness constraint. | Create a unique MongoDB index on `emp_code` and handle duplicate-key errors. |
| 5 | `create_employee()` | The starter does not validate that the employee record is usable before creating attendance records. | Try creating an employee with invalid shift or date values, or punching in with an unknown employee code. | Validate request fields and return a suitable client error when an employee or required value is invalid. |
| 6 | `list_employees()` | The skip calculation uses `page * page_size`, so page 1 skips the first page of results. The total also ignores the department filter. | With six employees and `page_size=5`, page 1 can skip the first five employees; a department-filtered response can report the unfiltered total. | Use `(page - 1) * page_size`, count documents using the same filter, and validate pagination parameters. |
| 7 | `punch_in()` | The starter does not handle an unknown employee before accessing `emp["shift_start"]`. It also relies on local machine time when converting timestamps and checking attendance dates. | Punch in using an unknown `emp_code`, or use an epoch timestamp near midnight where the UTC and IST dates differ. | Return a clear not-found error for unknown employees and consistently normalize timestamps and attendance dates to IST. |
| 8 | `punch_in()` | The duplicate check followed by insertion is vulnerable to concurrent requests; the lookup alone cannot guarantee one attendance record per employee per date. | Send simultaneous punch-in requests for the same employee and date. | Enforce uniqueness with a compound index on `emp_code` and `date`, and handle duplicate-key errors with HTTP 409. |
| 9 | `list_attendance()` | It loads every matching attendance document into application memory and sorts and paginates in Python. This becomes expensive on a large dataset. | Run the endpoint against a large attendance collection and observe memory usage and response time. | Apply filtering, sorting, counting, skipping, and limiting in MongoDB, supported by appropriate indexes. |
| 10 | `list_attendance()` | The starter returns MongoDB documents without consistently converting database-specific values into API-safe JSON values. | Request records containing MongoDB identifiers or other BSON-specific values and check JSON serialization. | Serialize identifiers and BSON values safely before returning API responses. |
| 11 | Analytics endpoints | The starter does not implement the required monthly analytics, department summary, late leaderboard, department trend, and explain endpoints. | Open `/docs` and compare the available routes with the required OpenAPI contract. | Implement the required endpoints and their aggregation pipelines, following the specified response schemas and business rules. |
| 12 | `present_days` aggregation in employee monthly and department summary analytics | Counting every presence-status record as a present day incorrectly includes weekends. The contract counts present days only from Monday through Friday. | Add a Saturday or Sunday attendance record and compare `present_days` with the expected weekday-only total. | Use MongoDB's `$dayOfWeek` to count only Monday–Friday for `present_days`; keep weekend records included in late and overtime totals. |
| 13 | Explain response serialization | MongoDB explain output can contain BSON-specific values that are not directly JSON serializable. | Call the explain endpoint and inspect whether serialization fails for the returned execution statistics. | Convert the explain result to Extended JSON and then to a JSON-compatible Python object before returning it. |

## Items Reviewed but Not Considered Defects

- **The `/health` endpoint:** Returning a simple status response is sufficient for the contract's basic health check; it does not need to return employee or attendance data.
- **A zero `late_minutes` value for an arrival no more than ten minutes late:** This is intentional because the rule treats an arrival as late only when it is strictly more than ten minutes after shift start.
- **Zero overtime when an employee leaves before the shift ends:** This is expected behavior; overtime cannot be negative.
- **A missing punch-out timestamp on an open attendance record:** This is a valid state for an employee who has punched in but has not yet punched out.
- **A separate unique index for employee code and a compound unique index for attendance employee/date:** These protect different uniqueness guarantees and are not redundant.
- **Weekend attendance records:** They should remain available for attendance history and contribute to late and overtime totals. Only the `present_days` calculation excludes weekends.
